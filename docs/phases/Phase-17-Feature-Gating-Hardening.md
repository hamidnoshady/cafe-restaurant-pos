# Phase 17 — Feature Gating & Platform Hardening

**Project:** Cafe/Restaurant POS
**Depends on:** Phase 12–16
**Goal:** The platform is safe to run for paying strangers: entitlements are enforced, tenants can't affect each other, and isolation is continuously proven rather than assumed.

---

## Scope

- **Flag-driven gating** — the feature flags Phase 12 modelled and Phase 15 administers actually gate UI and API. A disabled feature is hidden in the nav *and* refused at the guard, not just hidden.
- **Plan limits** — per-plan ceilings (branches, members, orders per month, storage) enforced at the point of creation with a clear Persian error, not a crash.
- **Per-tenant backup, restore and export** — the Phase 10 backup system currently assumes one business per database; make it export and restore a single tenant.
- **Tenant-scoped rate limiting** — one business's traffic or a runaway offline-sync client can't degrade another's.
- **Isolation test suite** — a systematic, generated test that for *every* tenant table attempts cross-tenant read, insert, update and delete, so a future migration that adds a table without a policy fails CI rather than production.
- **Performance under multi-tenancy** — index review for the new `business_id` predicates, RLS subplan cost on the hot order/inventory paths, and connection-pool sizing now that tenant-scoped queries pin a connection.
- **Security review** — a full pass over the tenant boundary: session forgery, business switching, the RLS bypass path, impersonation, and the token-authenticated server-to-server routes.

## Out of scope

- Horizontal scaling / read replicas.
- Data residency per tenant.

## Exit criteria

- Every tenant table is covered by the generated isolation test, and adding an uncovered table fails CI.
- A business on a plan without a feature cannot reach it by any route, including by hand-crafting the request.
- A single tenant's backup restores into a clean database without carrying any other tenant's rows.
- No regression against the Phase 9 performance baseline on the order and inventory hot paths.

## Decisions

1. **Enforcement is centralised in `withTenantScope`, not swept across every route file.** `feature_flags`/`business_features` (migration 0020) and Phase 15's admin write path already existed; the only gap was that nothing outside the platform console ever read them. Rather than adding a `requireFeature()` call to each of the ~9 flags' dozens of routes individually, `withTenantScope` (`src/lib/auth.ts`) itself resolves the request's pathname against a static prefix→flag mapping (`src/lib/features.ts`) and 403s before the handler ever runs, once a session exists. One change at the shared wrapper every route already goes through, rather than a hundred-file sweep — the same "one enforcement point, not an audited convention" instinct as the fiscal-period lock trigger in Phase 16.
2. **Page-level enforcement is a server-side redirect, not just an emptied-out UI.** Each gated dashboard page (`inventory`, `ledger`, `reservations`, `floor`, `waiter`, `delivery`, `reports`, `branches`, `locations`, `backup`, `ai`) calls `requireFeatureForPage(businessId, flag)` right where it already checks role, redirecting to `/dashboard` — matching the exit criterion's "cannot reach it by any route, including by hand-crafting the request" more literally than leaving the page reachable with every API call inside it 403ing.
3. **The `reservations` flag also gates floor/table management (`/dashboard/floor`, `/dashboard/waiter`, `/api/tables`, `/api/table-sessions`, `/api/floor`)**, not just the booking calendar — the flag's own catalogue description (migration 0020) already reads "رزرو میز و مدیریت سالن" (table reservation *and* floor/hall management), so this is executing existing product copy, not a new judgment call.
4. **`/api/locations` (branch-resolution: `resolveActiveLocation`, used by every session) is deliberately never gated by any flag** — it's core plumbing, not an optional feature. `/dashboard/locations` (the Phase 9 cross-server rollup admin page, a genuinely optional feature) is gated under `offline_mode` instead, matching that flag's "کار بدون اینترنت... همگام‌سازی سرور محلی" description.
5. **Plan limits, per-tenant backup, performance work, and the security review are not started at the time this decision was written** — the first two depend on the open questions above (actual tiers, block-vs-degrade behaviour, export format); the performance/security items were independent follow-on slices (the security review has since shipped; see decisions 7-8).
6. **The generated isolation check proves a policy's actual expression, not just that one exists.** The pre-existing structural check (RLS enabled + forced + ≥1 policy on every non-exempt table) catches a table added with *no* policy at all, but would pass just as happily if someone wrote `USING (true)` or checked the wrong column. A new generated test instead reads every table's `tenant_isolation` policy straight out of `pg_policy` (via `pg_get_expr`) and asserts its USING *and* WITH CHECK clauses both reference `app_rls_bypass()` and (`app_current_business()` or `app_owns_location()`) — covering every shape (direct `business_id`, `location_id`-via-`locations`, and every `EXISTS`-based child-table traversal) in one pass, with zero per-table synthetic data. `platform_users`' WITH CHECK is deliberately bypass-only (a platform identity is created before any business exists to link it to, at signup) and is the one documented exception.
7. **The security review's real findings got fixed, not just written up** — asked of the user first for the two disruptive ones (a forced global re-login, and changing a Phase 11 feature's auth model), since both carry real risk of breaking something already working rather than being pure implementation detail:
   - **Impersonation's "kill switch" didn't actually kill anything.** `activeGrant`'s own doc comment (`platform-service.ts`) already said it was "the check the impersonation guard runs on every request carrying an impersonation claim... so ending or revoking a window takes effect on the next request" — but nothing outside its own definition ever called it. Revoking or ending a grant stamped the database row; the already-minted tenant JWT kept working, completely unaffected, until its own `SESSION_HOURS` expiry (12h by default). `getSession()` (`src/lib/auth.ts`) now calls it for every session carrying an `imp` claim and treats a no-longer-live grant exactly like an invalid token — the one-line-summary fix for the phase's most severe finding.
   - **"Every impersonated action tagged in `platform_audit_log`"** (Phase 15's stated goal) only ever covered a grant's own start/end/revoke, not what was actually *done* with it. `withTenantScope` now logs an `impersonation.request` entry for every mutating request made under an active impersonation session — centralised at the same wrapper every route already goes through, so no per-route sweep was needed. `read_only` mode never reaches this (middleware 403s its mutations before the handler runs), so this fires exactly for the higher-trust `full` mode that can actually change a customer's data.
   - **Cross-realm token confusion.** The platform realm already stamped a `realm: "platform"` claim and rejected anything else; the tenant realm never checked a realm claim at all, so a platform-admin token would verify fine against `verifySession` and be trusted as a tenant session. Both directions now stamp and require a matching `realm` claim (`"tenant"` / `"platform"`) — the user approved this over documenting-only, accepting a one-time forced re-login for every active session (tokens last up to `SESSION_HOURS`/`PLATFORM_SESSION_HOURS`, 12h/2h by default) in exchange for actually closing the gap rather than relying on incidental shape differences downstream.
   - **Server-sync's receiving side (`/api/server-sync/push`/`/pull`) trusted one global `REMOTE_SYNC_TOKEN` env var and established no explicit tenant scope at all**, relying entirely on RLS being enforced on the DB connection — which this project's own stock `docker-compose.yml` runs as a superuser (RLS a silent no-op). Confirmed as a real, not just theoretical, gap: `/pull`'s query had no business filter whatsoever, so under a `BYPASSRLS` connection it would return literally every business's `sync_events`. The user approved hardening this over documenting an accepted-risk deployment assumption. See decision 8.
   - Lower-severity, zero-risk hardening applied in the same pass: pinned `algorithms: ["HS256"]` on every `jwtVerify` call (defense in depth — not currently bypassable, since `jose` already rejects a raw-secret key with `alg: "none"`); switched the server-sync bearer-token comparison from `!==` to a hashed, `timingSafeEqual`-based comparison; made the `JWT_SECRET`-unset dev fallback log a loud one-time warning instead of failing silently (kept the existing `NODE_ENV`-gated throw-in-production behaviour unchanged, since tightening it risks breaking CI/deployments this review has no visibility into — flagged as a documented, not auto-applied, follow-up); relabelled `team-service.ts`'s `setPassword` bypass from the misleading `"platform"` to `"identity"`, since it's an ordinary owner-in-business action, not platform administration, and updated the three places that enumerate legitimate bypass reasons (`tenant-context.ts`, `db.ts`, this doc) to include the two new categories (`"server-sync-auth"`, `"identity"`) alongside the original two (`"login"`, `"platform"`).
8. **Server-sync gets a per-business hashed token (`server_sync_tokens`, migration 0033), mirroring `rollup_locations.token_hash` exactly**, resolved before any tenant is chosen (the same bypass category as login). The legacy global `REMOTE_SYNC_TOKEN` env var stays as a fallback for anyone who hasn't configured a per-business token yet — but even on that path, the business is now derived explicitly (from the pushed events' own locations for `/push`, required to all agree; from an explicit `?businessId=` for `/pull`, since it has no location data to derive one from) and every read/write is wrapped in `withTenant()`, so the tenant boundary no longer depends on RLS alone regardless of which token model is in use.
9. **A follow-up fix, found while researching rate limiting: `/api/server-sync/push` and `/api/server-sync/pull` were never in `middleware.ts`'s `PUBLIC_PATHS`**, unlike the equivalent Phase 9 route (`/api/rollup/ingest`), which was. Every real bearer-token request was rejected with a bare 401 by middleware's generic "no session cookie" branch before it ever reached the route's own token check — server-sync (and everything built on top of it in decision 8) has been unreachable in practice regardless of token validity. Confirmed pre-existing via `git log --follow` and fixed by adding both paths to the allowlist; verified live that both routes now return their own `{error:"unauthorized"}` body instead of middleware's short-circuit.
10. **Tenant-scoped rate limiting is centralised in `middleware.ts`, the one place every request already passes through — not swept per-route, and not backed by a store that needs the database.** Investigation found zero existing rate-limiting infrastructure, real-time UI updates run over a WebSocket (`/ws`, handled by `server.ts`'s own upgrade handler, never reaching Next's request pipeline or this middleware) rather than HTTP polling, and the only periodic client HTTP traffic is `offline-queue.tsx`'s 15-second flush — all of which meant there was no existing traffic pattern a limiter needed to accommodate beyond ordinary interactive use. `src/lib/rate-limit.ts` is a pure, store-agnostic fixed-window counter (`checkRateLimit`) plus a `sweepExpired` cleanup and a `hashKey` helper (a non-cryptographic hash used only to keep raw bearer tokens out of the limiter's map keys, never for anything security-sensitive), covered by `rate-limit.test.ts`. `middleware.ts` owns three module-level maps and applies three limits: (a) 300 req/60s per `session.businessId` on every authenticated tenant API request — the literal exit criterion, "one business's traffic ... can't degrade another's"; (b) 60 req/60s per bearer token (hashed) on the session-less server-to-server routes (`rollup/ingest`, `server-sync/push`, `server-sync/pull`) — middleware can't resolve a token to a business without the database, so a runaway sync client is capped by its own token instead; (c) 20 req/60s per IP on the credential-exchange endpoints (`auth/login`, `auth/pin-login`, `platform/auth/login`), which had no other request-volume defence. Over the limit returns 429 with `{error:"rate_limited"}` and a `Retry-After` header. Verified live: flooding `auth/login` from one IP hits 429 with a counting-down `Retry-After` on request 21, a different IP is unaffected by the same flood, and ordinary traffic (including the sync routes with a real/absent token) passes through untouched.
11. **Multi-tenancy performance review — first established what "no regression against the Phase 9 baseline" could even mean, since Phase 9 never measured one.** Its own "Performance pass" (see that phase's doc) covered two ad hoc index additions with no recorded numbers and `scripts/ws-load-test.ts`, which measures WebSocket fan-out latency (13-21ms range), not order-creation or payment/inventory-consumption DB latency. There was nothing numeric to regress against on the actual hot path, so this review's job was to (a) prove the RLS design decisions already made are holding up under realistic data volume, (b) review indexing, (c) review pool sizing, and (d) capture that missing first baseline:
    - **RLS subplan cost — proven, not just designed-in.** Migration 0021's Shape 2 comment already states the intent ("the planner hashes \[the location_id IN (SELECT …) form\] into a single subplan per statement, where a per-row helper function would be evaluated once per row") but nothing had tested it. `integration/query-performance.integration.test.ts` seeds realistic volume (thousands of rows, 50 "noise" businesses so one business's slice is a small, selective fraction of each table rather than the whole table) and asserts, via `EXPLAIN (ANALYZE, FORMAT JSON)` against the unprivileged app role: the hot tables (`orders`, `order_items`, `inventory_items`, `stock_movements`) are still reached through an index for the query's own predicate, and every plan node touching `locations` (what the RLS subquery reads) has `Actual Loops = 1` — hashed once, not re-evaluated per row. First run against synthetic data with only one business's own rows in each table failed exactly as expected (Postgres correctly chose a Seq Scan when a query matched ~100% of a table — the right call, and a reminder that a plan-shape test is only meaningful at realistic scale/selectivity); adding the noise businesses fixed it and all five assertions now hold.
    - **Index review — no gap on the hot write path.** Every table in the order/payment/inventory-consumption path already carried the `location_id`/`inventory_item_id` index RLS now also needs, because location-scoped filtering predates RLS by several phases. The one table without a `business_id`/`location_id` index, `inventory_negative_layers`, was deliberately left alone: its only hot-path query (`purchase-receipt-costing.ts`) filters by `inventory_item_id` against the existing partial index `idx_inventory_negative_layers_open`, which already narrows to a handful of rows for one item before RLS's `business_id` predicate is even applied — adding an index there would protect a query that doesn't exist yet, not the hot path.
    - **Pool sizing made configurable, not re-guessed.** `max: 20` had no stated basis. Rather than picking a new arbitrary number, `src/lib/pool-config.ts`'s `poolMax()` reads `DB_POOL_MAX` (falling back to the same 20, so nothing changes for anyone who doesn't set it) — the right ceiling depends on how many businesses' concurrent write transactions one deployment expects to pin a connection for, which varies by deployment (one café vs. several sharing a host) and isn't this review's call to make unilaterally.
    - **First order/inventory latency baseline captured.** `scripts/order-perf-benchmark.ts` (mirrors `ws-load-test.ts`'s login/percentile pattern) drives real `POST /api/orders` and `POST /api/orders/:id/pay` calls against a running, seeded server and reports p50/p95/max. A 100-round run against this repo's dev sandbox (Next dev server, not a production build; single local Postgres sharing the host with the agent process — read as a rough baseline for future comparison, not a production SLA) recorded: order creation p50 113ms / p95 173ms / max 339ms; payment (inventory consumption + ledger postings) p50 140ms / p95 185ms / max 2.7s (one outlier). Future changes to this path should re-run the script and compare against these numbers.
12. **Plan limits: three proposed tiers (`free`/`pro`/`business`), block-not-degrade, enforced per creation path since there's no single chokepoint for it.** `businesses.plan` (migration 0020) had been a free-text label with no catalogue and no limits ("Plans are assigned by hand (no billing)"). Migration 0034 gives it one: a `plans` table (same shape as `feature_flags` — a global catalogue, no RLS, since every business reads the same few rows) seeded with `free` (1 branch / 5 members / 500 orders per month), `pro` (5 / 20 / 5,000), and `business` (all three `NULL` = unlimited); pre-existing free-text plan values that don't match a catalogue key are normalised onto `pro` in the same migration, and `businesses.plan` gained an FK to `plans.key` so it can no longer drift to an undefined value again. Unlike feature flags (a static path→flag lookup, checked once centrally in `withTenantScope`), a plan limit needs a `COUNT(*)` specific to the action being taken, so `src/lib/plan-limits.ts`'s functions are called individually at each of the four places a limit-relevant row is actually created, right before the INSERT: `createBranch` (branch-service.ts), `createMembership` and `acceptInvitation` (team-service.ts — both membership-creation paths), and `createOrder` (order-mutations.ts, counting the current calendar month across every branch of the business). Exceeding a limit blocks that one action with a `{error: "<resource>_limit_exceeded"}` 403 (the product owner's choice over degrading existing usage) and a Persian message in the existing `errorMessage` dictionaries (`dashboard/ui.tsx`, mirroring the same pattern every other API error code already uses). The platform console's plan panel (`/platform/businesses/[id]`) changed from a free-text input to a `<select>` populated from a new `GET /api/platform/plans` route, showing each tier's actual limits so an operator isn't guessing at a label; assigning an unrecognised plan now 400s with `invalid_plan` instead of hitting the FK at the database. Verified in `integration/plan-limits.integration.test.ts` (10 tests: each of the four creation paths blocked exactly at its plan's cap, the `business` tier proven genuinely unlimited by exceeding every default tier's cap, and — the same isolation story as the rest of this phase — one business sitting at its own cap never affects another's) and live via Playwright against the platform console (the select renders all three tiers with correct Persian-digit limits, changing and saving a plan persists across reload, and an invalid plan is rejected before reaching the database).

13. **Per-tenant export ships (both formats, per the product owner's decision); restore is a separate, not-yet-built follow-up.** The Phase 10 backup system is documented as "one business per install" — `pg_dump --format=custom` of the whole physical database, and `pg_dump` has no row-level filter to retrofit for one business's slice. Rather than reimplementing each table's RLS shape (direct `business_id`, `location_id`-via-`locations`, `EXISTS`-based child) to know how to filter it, `src/lib/tenant-export.ts`'s `exportTenantData(businessId)` just runs `SELECT * FROM <table>` for every tenant table **inside `withTenant(businessId)`** — RLS itself does the filtering, for every shape, without the exporter ever needing to know which shape a given table uses. `src/lib/tenant-tables.ts` is the reusable "every tenant table" enumeration `tenant-isolation.integration.test.ts` used to only have inline, plus a topological sort over `pg_constraint`'s foreign keys so a table is always exported/restored after every table its FKs point to, and a row-level sort (`sortRowsByParent`) for the one self-referencing table in the schema (`accounts.parent_id`) so a parent account is always inserted before its child even within that one table. Two render formats reuse this same `TenantExportTable[]` shape: `tenantDataToSql` (restorable INSERT statements, using Postgres's own `'{a,b}'` array-literal text form rather than `ARRAY[...]` specifically because an *empty* array — e.g. `invitations.location_ids`'s default `'{}'` — can't be typed via the `ARRAY[]` constructor without a cast, while `'{}'` parses via the same assignment-cast mechanism every other scalar value here relies on) and `tenantDataToXlsxBuffer` (one workbook, one sheet per table, reusing `report-export.ts`'s `cellValue` — extended to `JSON.stringify` objects/arrays instead of stringifying them as `"[object Object]"`). `GET /api/backup/export?format=sql|xlsx` is Owner-only (a materially higher bar than "backup now"'s Owner/Manager, since this hands the browser literally all of a business's data), surfaced as two buttons on `/dashboard/backup`. **A real bug caught by the round-trip test, not just reasoned about:** `listForeignKeys()`'s first version read `information_schema.constraint_column_usage`, which — unlike `pg_catalog` — silently hides rows the querying role lacks certain privileges on; run as the unprivileged app role (not the table owner), it dropped the `accounts → businesses` edge entirely, which put `accounts` before `businesses` in the generated dump and made the restore fail on `accounts_business_id_fkey`. Switched to reading `pg_constraint`/`pg_class` directly (the same pg_catalog-not-information_schema instinct `tenant-isolation.integration.test.ts` already uses for policy introspection), with a regression test pinning that specific edge. Verified in `integration/tenant-export.integration.test.ts` (5 tests: only the requested business's rows come out with a second business's data present in the same tables, the self-referencing `accounts` table orders correctly, empty tables are omitted, and — the literal exit criterion — the generated SQL applied to a second, separately-migrated, empty database reproduces exactly that business's rows and nothing from the other business) and live via Playwright against a running server (both downloads succeed with correct content-type and non-trivial content). Restoring that SQL through an actual guided workflow (dry-run-then-apply, mirroring Phase 10's own restore UX) is deliberately left for a follow-up slice — this covers the export half of the scope item plus a proven, correct SQL format for the restore half to build on.

## Progress

- **Flag-driven gating — implemented.** `src/lib/features.ts` is the read side of Phase 15's write side (`platform-service.ts`'s `businessFeatures`/`setBusinessFeature`): `effectiveFeatures(businessId)` resolves every flag's per-business override against its catalogue default, `isFeatureEnabled` checks one, and `featureForApiPath`/`featureForPagePath` are pure prefix-matchers (decision 3/4) mapping a request path to the flag that gates it. `withTenantScope` (`src/lib/auth.ts`, decision 1) 403s with `{error: "feature_disabled", flag}` before the handler runs whenever a session exists and its business has the matched flag off. Each of the 11 gated dashboard pages calls `requireFeatureForPage` (decision 2) alongside its existing role check; `src/app/dashboard/layout.tsx` fetches `effectiveFeatures` once and filters `NAV_ITEMS` (extended with an optional `flag` field) before it ever reaches the sidebar, and the floating AI assistant widget only mounts when `ai_assistant` is on. Verified in `src/lib/features.test.ts` (the pure path-matchers, including that `/api/locations` and unmapped prefixes like `/api/team` stay ungated) and `integration/feature-gating.integration.test.ts` (an override disabling a default-on flag, enabling a default-off one, clearing an override falling back to the default, and one business's override never leaking to another's) against a real server. Manually verified end-to-end: disabled `inventory` for a fresh business via a direct `business_features` row (what the platform console's toggle writes) and confirmed all three surfaces at once — the sidebar no longer showed "انبار", navigating straight to `/dashboard/inventory` redirected to `/dashboard`, and a hand-crafted `GET /api/inventory` returned 403 — while an unrelated flag (`ledger`) and page stayed completely unaffected; re-enabling it restored all three immediately.
- **Isolation test suite — the generated coverage is strengthened; the exit criterion is met.** `integration/tenant-isolation.integration.test.ts` already generated its *coverage* check (every non-exempt live table must have RLS enabled, forced, and ≥1 policy) straight from `pg_class`/`pg_policy`, so "adding an uncovered table fails CI" was already true. What it didn't generate was proof that each policy's own expression is *correct*, not just present (decision 6) — a new test now reads every `tenant_isolation` policy's USING/WITH CHECK text via `pg_get_expr` and asserts both reference the tenant boundary, covering all four RLS shapes (direct `business_id`, `location_id`-via-`locations`, single- and multi-level `EXISTS` child traversals) in one exhaustive, data-free pass. Also added one more hand-written behavioural attack test — `business_features` (a direct-`business_id` table, and the exact one Phase 17's own feature-gating enforcement reads per request) — alongside the pre-existing spot-checks (`menu_categories`/`orders` for `location_id`-scoped tables, `journal_entries`/`journal_lines` for a business_id-table-plus-its-child, `businesses`/`platform_users` for the tenant root and cross-business identity). Verified: the new tests pass against the live schema (19 tests total in this file, up from 17) with no regressions across the rest of the suite.
- **Security review — implemented.** See decisions 7-9: impersonation revocation/expiry is now actually enforced (`checkImpersonation` in `getSession()`), every mutating request under impersonation is audit-tagged, the tenant and platform realms now reject each other's tokens via a required `realm` claim, server-sync moved off one global shared token onto per-business hashed tokens with explicit `withTenant()` scoping (migration 0033), and a pre-existing bug that made server-sync completely unreachable (missing `PUBLIC_PATHS` entries) was found and fixed. Covered by `integration/impersonation.integration.test.ts`, `integration/server-sync-tokens.integration.test.ts`, `auth-edge.test.ts`, and `platform-auth-edge.test.ts`.
- **Tenant-scoped rate limiting — implemented.** See decision 10: `src/lib/rate-limit.ts` (a pure fixed-window counter, unit-tested in `rate-limit.test.ts`) backs three in-memory limits in `middleware.ts` — per-business (300/60s), per-sync-token (60/60s), and per-IP on login endpoints (20/60s) — all returning 429 with `Retry-After` when exceeded. Verified live against a running server.
- **Multi-tenancy performance review — implemented; exit criterion met on the measurable part of it.** See decision 11: `integration/query-performance.integration.test.ts` proves the Shape 2 RLS policy's subplan-cost design holds at realistic scale (index-backed hot-table access, single-evaluation `locations` subquery); the index review found no gap on the hot write path; `src/lib/pool-config.ts` makes pool sizing a `DB_POOL_MAX` env var instead of a re-guessed constant; `scripts/order-perf-benchmark.ts` captured the first-ever order/payment latency baseline, since Phase 9 never measured one for this path (only WebSocket fan-out). "No regression against the Phase 9 baseline" now has something concrete to mean going forward, even though Phase 9 itself left nothing to compare against retroactively.
